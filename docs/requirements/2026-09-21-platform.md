# EXTENSIÓN DE ARQUITECTURA — PACHAX PLATFORM ADMIN

Además de todo el trabajo descrito anteriormente, necesitamos una capa administrativa exclusiva de PACHAX.

IMPORTANTE:

Esto NO es un rol normal dentro de un tenant.

No es:

`tenant admin`

No es:

`restaurant admin`

No es:

`distribution admin`

Debe existir conceptualmente:

# PACHAX PLATFORM

por encima de todas las empresas.

La estructura final debe distinguir claramente:

```text
PACHAX PLATFORM
    |
    ├── Templates
    │     ├── restaurant_pos
    │     ├── route_distribution
    │     └── gelateria_weight_cafe
    │
    └── Tenants / Empresas
          ├── Empresa A
          ├── Empresa B
          ├── Empresa C
          └── ...
```

Necesito que mi usuario interno de PACHAX pueda administrar y dar soporte a toda la plataforma sin utilizar múltiples correos de clientes.

---

# 1. ROLES DE PLATAFORMA

Crear una capa de autorización diferente a los roles internos de cada empresa.

Conceptualmente:

```text
platform_owner
platform_admin
platform_support
platform_finance
```

Por ahora mi usuario principal será:

`platform_owner`

Este usuario debe poder acceder a todo el Centro de Control PACHAX.

Los demás roles deben quedar preparados arquitectónicamente, aunque no necesitamos desarrollar cada permiso extremadamente granular todavía.

## platform_owner

Acceso total administrativo a PACHAX.

## platform_admin

Administración de empresas, plantillas y soporte.

## platform_support

Acceso orientado a diagnóstico y soporte.

No debe recibir automáticamente funciones financieras o extremadamente sensibles si no las necesita.

## platform_finance

A futuro:

* suscripciones;
* facturación PACHAX;
* MRR;
* ARR;
* pagos;
* deuda;
* planes.

Por ahora puede quedar preparado pero no es necesario habilitarlo.

---

# 2. SEGURIDAD DE CUENTAS DE PLATAFORMA

NO almacenar simplemente:

```text
users/{uid}.role = "platform_owner"
```

si cualquier cliente puede modificar ese documento.

La condición de usuario PACHAX Platform debe ser segura.

Evaluar la mejor implementación según la arquitectura existente:

* Firebase Custom Claims;
* colección protegida server-side;
* o combinación de ambas.

Un tenant NO puede convertirse a sí mismo en platform admin.

Un usuario normal NO puede asignarse:

`platform_owner`

Las reglas Firestore deben distinguir claramente:

```text
tenant membership
```

de:

```text
platform authorization
```

Crear tests del emulador para esto.
